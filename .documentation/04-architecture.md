# Архитектура: FSD + переносимость между фреймворками

> Требование владельца: декомпозиция должна позволять сменить фреймворк (например, Astro → Next.js) максимально безболезненно. Готовый UI-кит, фичи и слайсы переезжают как есть; фреймворк-специфика живёт только в тонком слое приложения.

## Слои FSD

```
src/
├── app/        # ЕДИНСТВЕННОЕ место фреймворк-специфики: layouts, роутинг,
│               # интеграция Content Collections, astro:assets, темы-инициализация
├── pages/      # тонкие страницы: только композиция виджетов + вызов SEO-хелперов
├── widgets/    # header, footer, product-gallery, how-we-work, contacts
├── features/   # theme-toggle, order-form, lightbox, phone-call
├── entities/   # product, category, company — типы, схемы, карточки
└── shared/     # ui-кит, дизайн-токены, lib, config, seo
```

Импорты строго сверху вниз (app → pages → widgets → features → entities → shared), доступ к слайсу — только через его `index.ts`. Внутри слайса файлы раскладываются по сегментам (`ui/`, `model/`); контроль — Steiger + eslint-plugin-boundaries.

**Astro-адаптации FSD (задокументированные исключения):**

- `pages` → `app`: страницы Astro подключают `app/layouts/base-layout.astro` — в чистом FSD слой pages не импортирует app, но в Astro лайаут технически подключается страницей.
- `src/pages/index.astro` — роут главной, а не public API слоя (правило `fsd/no-layer-public-api` отключено для pages).
- Правило `fsd/insignificant-slice` отключено: Steiger не разбирает импорты в `.astro`-файлах.

## Принцип переносимости: «тонкий шаблон»

Каждый слайс раскладывается на три вида файлов:

| Файл      | Содержимое                                                                                               | При миграции                                             |
| --------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| `*.ts`    | Вся логика, типы, данные, константы. **Чистый TypeScript, ноль импортов из `astro:*` или jsx**           | Переезжает без изменений                                 |
| `*.css`   | Стили на CSS-токенах (custom properties), обычные классы, `light-dark()` для тем. Без scoped-магии Astro | Переезжает без изменений                                 |
| `*.astro` | Только разметка: подключает css, дёргает функции из ts, навешивает классы и data-атрибуты                | Единственное, что переписывается (механически, в `.tsx`) |

Пример слайса:

```
features/theme-toggle/
├── index.ts          # публичный API
├── model.ts          # логика: чтение/запись темы, prefers-color-scheme — чистый TS
├── theme-toggle.css  # стили кнопки на токенах
└── ui.astro          # <button> с data-атрибутами, подключает model через <script>
```

## Правила, обеспечивающие переносимость

1. **Запрет фреймворк-импортов вне `app/` и `pages/`**: в `shared/`, `entities/`, `features/`, `widgets/` нельзя импортировать `astro:content`, `astro:assets` и пр. Закрепляется правилом `eslint-plugin-boundaries` / `no-restricted-imports`, а не договорённостью.
2. **Данные через адаптеры**: `entities` объявляют интерфейсы (`Product`, `Category` + zod-схемы); `app/` содержит адаптер, который маппит Astro Content Collections на эти интерфейсы. При миграции меняется только адаптер.
3. **Интерактив — vanilla TS + data-атрибуты**: фичи (переключатель темы, лайтбокс, валидация формы) — чистые функции `init*(root: HTMLElement)`, которые в Astro вызываются из `<script>`, а в Next.js — из `useEffect`. Никакой логики внутри разметки.
4. **UI-кит без состояния**: `shared/ui` — презентационные компоненты (Button, Section, Card, Badge…), вся вариативность через пропсы-классы и CSS-токены. Один компонент = одна папка: `component.css` + `component.astro` (+ `types.ts`).
5. **Дизайн-токены — единственный источник стиля**: `shared/config/tokens.css` (цвета обеих тем через `color-scheme`/`light-dark()`, типографика, отступы, брейкпоинты). Компоненты не содержат «сырых» значений.
6. **SEO — чистые функции**: `shared/seo` генерирует объекты JSON-LD, title/description, OG — возвращает данные, а вставляет их в `<head>` только `app/layouts`.
7. **Изображения через обёртку**: единственный компонент `shared/ui/picture`, внутри которого Astro-оптимизация. Остальной код зависит только от его пропсов — при миграции меняется одна обёртка на `next/image`.

## Итог миграции Astro → Next.js

Переписываются: `.astro`-шаблоны (механический перенос разметки в `.tsx`), адаптер данных в `app/`, обёртка `picture`, layouts/роутинг. Не трогаются: вся логика, типы, схемы данных, стили, токены, SEO-генераторы, контент — то есть ~80% кодовой базы.
